# Scalwise Media — Production Deployment (6a) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Get the existing Scalwise Media site live on Vercel against production Postgres (Neon), with real Payload migrations instead of dev-mode schema push, and working file uploads via Vercel Blob storage.

**Architecture:** Two code changes land first — a generated Payload migration wired into the build command, and a conditionally-enabled Vercel Blob storage plugin for the `Media` collection — both committed and pushed to the existing GitHub repo. Then Vercel/Neon/Blob get provisioned through Vercel's dashboard (manual, account-gated steps), which auto-populates the needed environment variables. The next deploy runs migrations as part of the build, then serves the app.

**Tech Stack:** Next.js 16 (App Router), Payload CMS 3.88, `@payloadcms/db-postgres`, Neon Postgres, Vercel (hosting + Blob storage), GitHub (already connected as `origin` → `Aditya-051028/Swastik-Website`).

## Global Constraints

- No custom domain, SEO metadata, sitemap/robots/JSON-LD, Lighthouse pass, or accessibility audit in this plan — all deferred to the separate 6b spec/plan.
- No sub-project 3 (rate limiting/email), 4 (content), or 5 (integrations) work — no Upstash, Resend, WhatsApp, Calendly, or analytics env vars introduced here.
- `@payloadcms/storage-vercel-blob` must be pinned to `3.88.0` to match the installed `payload` core version exactly (verified via `npm view @payloadcms/storage-vercel-blob version peerDependencies` during brainstorming).
- Local dev behavior must not change: `next dev` keeps using push-based schema sync against the local Homebrew Postgres DB, and `Media` uploads keep going to local disk when `BLOB_READ_WRITE_TOKEN` is unset — verified against the installed adapter's own source (`node_modules/@payloadcms/db-postgres/dist/connect.js`), which only skips push when `NODE_ENV === 'production'`.
- All new secrets (`PAYLOAD_SECRET` for production, `DATABASE_URL`, `BLOB_READ_WRITE_TOKEN`) are set in the Vercel dashboard only — never committed, matching the existing `.gitignore` convention for `.env*`.
- TypeScript strict mode; `npx tsc --noEmit` and `npm run lint` must stay clean after every task (existing project convention, `PROJECT_CONTEXT.md` §10).

**Files:**

- Modify: `package.json:7` (the `build` script)

**Interfaces:**

- Produces: a `migrations/` directory with an initial migration capturing the current schema, and a `build` script (`payload migrate && next build`) that Task 4's deploy relies on.

- [ ] **Step 1: Confirm local Postgres is up and matches current schema**

Run: `brew services list | grep postgresql` — confirm `postgresql@17` shows `started`.

Then run `npm run dev`, load `http://localhost:3000/admin`, confirm it loads without schema errors, then stop the dev server (Ctrl+C). This confirms the local DB's push-synced schema is current before snapshotting it into a migration.

- [ ] **Step 2: Generate the initial migration**

Run:

```bash
CI=true npx payload migrate:create initial_schema
```

(`CI=true` avoids the interactive confirmation prompt — the same fix already used for `src/seed.ts`, documented in `PROJECT_CONTEXT.md` §11.)

Expected: a new `migrations/` directory appears at the repo root containing a timestamped file such as `migrations/<timestamp>_initial_schema.ts`, plus a matching snapshot file.

- [ ] **Step 3: Verify the migration captures the full schema**

Run: `ls migrations/`, then open the generated `*_initial_schema.ts` file. Confirm the `up` function creates tables covering all 7 collections (`users`, `media`, `leads`, `services`, `pricing`, `testimonials`, `case_studies`, `blog_posts`, `faqs`) and the `site_settings` global. Cross-check this list against `payload.config.ts`'s `collections` (lines 27–37) and `globals` (line 38) arrays.

- [ ] **Step 4: Wire migrations into the build command**

Edit `package.json` line 7, change:

```json
"build": "next build",
```

to:

```json
"build": "payload migrate && next build",
```

- [ ] **Step 5: Verify the new build command works against an empty database**

The real local dev DB (`scalwise_media`) already has every table from push — running `payload migrate` against it will fail with "relation already exists", since this is the first migration ever created and there's no tracking-table record that would let it recognize the schema as already satisfied. That failure is expected and is not a bug: production (Neon) starts empty, so this conflict never occurs there. Don't run `payload migrate:fresh` or otherwise touch `scalwise_media`'s tables to work around this — that would destroy its seeded data.

Instead, verify against a throwaway empty database that actually mirrors production's starting state:

```bash
createdb scalwise_media_migration_test
DATABASE_URL=postgresql://$(whoami)@localhost:5432/scalwise_media_migration_test npm run build
```

Expected: `payload migrate` applies the new migration cleanly against the empty DB, then `next build` completes successfully. This is the exact command Vercel will run, just pointed at an empty DB instead of Neon.

Then clean up:

```bash
dropdb scalwise_media_migration_test
```

The real dev DB keeps using push via `next dev`, unchanged — the `build` script's migrate step only ever runs in production/CI, never locally.

- [ ] **Step 6: Typecheck and lint stay clean**

Run: `npx tsc --noEmit && npm run lint`

Expected: both exit with no errors.

- [ ] **Step 7: Commit**

```bash
git add migrations/ package.json
git commit -m "Add initial Payload migration, run it before build in production"
```

### Task 2: Add Vercel Blob storage for media uploads

**Files:**
- Modify: `package.json` (new dependency)
- Modify: `payload.config.ts:1-6` (imports), `payload.config.ts:38` (insert `plugins` array after `globals`)

**Interfaces:**
- Consumes: nothing from Task 1.
- Produces: a conditional `vercelBlobStorage` plugin wired into Payload's config, active only when `process.env.BLOB_READ_WRITE_TOKEN` is set. Task 3 (Vercel dashboard setup) creates the Blob store that populates that token in production.

- [ ] **Step 1: Install the adapter, pinned to the matching Payload version**

Run:

```bash
npm install @payloadcms/storage-vercel-blob@3.88.0
```

Expected: `package.json` gains `"@payloadcms/storage-vercel-blob": "3.88.0"` under `dependencies` — its peer dependency is `payload: 3.88.0`, matching the installed core version exactly.

- [ ] **Step 2: Add the conditional plugin to payload.config.ts**

Add this import alongside the existing ones at the top of `payload.config.ts`:

```ts
import { vercelBlobStorage } from "@payloadcms/storage-vercel-blob";
```

Add a `plugins` array to the `buildConfig({...})` call, inserted immediately after `globals: [SiteSettings],`:

```ts
  plugins: [
    ...(process.env.BLOB_READ_WRITE_TOKEN
      ? [
          vercelBlobStorage({
            collections: { media: true },
            token: process.env.BLOB_READ_WRITE_TOKEN,
          }),
        ]
      : []),
  ],
```

When `BLOB_READ_WRITE_TOKEN` is unset (local dev today), the array is empty and `Media.ts`'s existing `staticDir: "media"` local-disk config governs uploads exactly as before — no local behavior change. When the token is set (Vercel, after Task 3), the plugin activates and Payload automatically disables local storage for the `media` collection in favor of Blob.

- [ ] **Step 3: Verify locally with the token unset**

Run: `npx tsc --noEmit`
Expected: no errors — confirms the import and conditional syntax are valid.

Run: `npm run dev`, load `http://localhost:3000/admin`, log in, open the Media collection, and upload a small test image.
Expected: the upload succeeds and the file appears under `public/media/` locally — confirms the empty-plugins-array path still uses local disk storage, unchanged.

- [ ] **Step 4: Commit**

```bash
git add package.json package-lock.json payload.config.ts
git commit -m "Add conditional Vercel Blob storage for media uploads"
```
